## 1. 总原则：三层适配模型

本工具对日志内容的依赖分三层，从浅到深：

```
┌─────────────────────────────────────────────────────┐
│ 第零层  日志格式解析（parser.py）                      │
│   能否把一行文本切成 {时间, 线程, 级别, Logger, 消息}     │
├─────────────────────────────────────────────────────┤
│ 第一层  分析模版（templates/*.json）                   │
│   模型按什么方向、什么格式去分析 —— 纯数据，零代码         │
├─────────────────────────────────────────────────────┤
│ 第二层  压缩去噪关键词（compressor.py）                 │
│   哪些日志是例行刷屏（计数化），哪些是失败（保留原文）       │
├─────────────────────────────────────────────────────┤
│ 第三层  统计口径（stats.py）                            │
│   失败事件判定、业务量统计、监控指标提取 —— 强业务耦合      │
└─────────────────────────────────────────────────────┘
```

**接入新项目的决策树**：

- 只关心「模型帮我读日志、总结问题」→ **只做第一层**（建个模版就完事，10 分钟）
- 还想要「失败事件精确计数、业务量统计、监控图表」→ 第三层必须适配（半天~一天）
- 第二层强烈建议顺带做（不做的话压缩率低、token 费，但功能不受影响）

## 2. 快速判断：你的日志属于哪种情况

拿新项目的日志样例，先回答两个问题：

**Q1：日志行首是不是「时间戳 线程 级别 Logger」结构？**

当前 parser.py 内置两种格式（见 §3），都是 Logback/Log4j 风格：

```
格式一（空格分隔）：2026-09-03 14:18:00.015 [biz-pool-11] ERROR c.y.c.X - 消息
格式二（竖线分隔）：2026-09-03 14:18:00|[biz-pool-11]|ERROR|c.y.c.X|消息
```

- 是 → 直接用，进入 Q2
- 否（如 JSON 行、自定义格式）→ 需要改 parser.py（§3）

**Q2：需要精确统计（失败次数/业务量/线程池）吗？**

- 不需要，模型分析够了 → 只做 §4
- 需要 → 做 §4 + §5 + §6

## 3. 第零层：日志解析适配（parser.py）

### 3.1 现状

文件：[core/parser.py](file:///c:/Users/11364/Desktop/log-analysis/core/parser.py)

两个正则 `HEAD`（空格分隔）与 `HEAD_PIPE`（竖线分隔），逐行匹配，不匹配的行归属上一条记录（多行堆栈/载荷）。产出的记录结构：

```python
{"ts": "2026-09-03 14:18:00.015",   # 时间戳，必须含毫秒（下游 strptime 依赖）
 "thread": "biz-pool-11",
 "level": "ERROR",                   # TRACE/DEBUG/INFO/WARN/ERROR/FATAL
 "logger": "c.y.c.t.i.CompositionGradingTask",
 "msg": "...",                       # 消息 + 后续续行（\n 连接）
 "line_no": 3594}                    # 起始行号
```

### 3.2 适配新格式的方法

**情形 A：仍是 Logback 风格，只是分隔符/时间格式微差**

在 parser.py 顶部加一个新正则（模仿 `HEAD_PIPE` 的写法），在 `parse_file` 里依次尝试匹配。两个注意点：

1. **时间戳必须补齐毫秒**（`.000`），否则 `collect_threadpool` 的 `strptime("%Y-%m-%d %H:%M:%S.%f")` 会抛异常
2. 多行合并逻辑（非头部行归属上一条）对新格式自动生效，不用改

**情形 B：完全不同的格式（如 JSON 行、logfmt）**

同样思路：写一个「识别一条记录起始行」的正则或 JSON 解析，产出上面 5 个字段的 dict。字段凑不齐的：

- `thread`/`logger` 可以填 `""`（仅影响压缩归并的分组键和展示）
- `ts` **必须有**且格式统一（分桶、时间跨度全靠它）
- `level` 建议有；没有就填 `"INFO"` 并在 `_is_routine` 相关逻辑里留意误判

**情形 C：一行一条、无多行载荷**

无需改合并逻辑，parser 会自然退化。

### 3.3 验证方式

```powershell
python -c "from core.parser import parse_file; rs = list(parse_file(r'新日志.log')); print(len(rs)); print(rs[0])"
```

解析条数 > 0 且字段齐全即通过。**解析失败 = 压缩输出为空 = 全盘失败**，这是历史上真实踩过的坑（见 project_memory 教训）。

## 4. 第一层：分析模版适配（零代码，最常用）

文件位置：`templates/*.json`，页面「+ 编辑模版」可视化编辑，后端 `POST /api/templates` 保存。

### 4.1 模版字段说明

```json
{
  "name": "日常巡检-某订单系统",
  "concern": "关注订单流转失败和支付超时",           // 分析方向总述
  "focus": ["支付超时", "库存不足", "重试风暴"],      // 关注点列表
  "outputFormat": "按「结论/风险/建议」三节输出",      // 输出格式要求
  "extraRules": "失败需给出 traceId 和时间点；忽略健康检查噪音",  // 附加规则
  "is_default": false
}
```

### 4.2 模版如何进入模型分析

[core/analyzer.py](file:///c:/Users/11364/Desktop/log-analysis/core/analyzer.py) 的 `render_prompt` 把模版字段 + 代码统计摘要 + 压缩后的日志分块拼成提示词。**模版是纯数据，新项目零代码**：

1. 页面上「+ 编辑模版」→ 新建
2. 按新项目的关注点填写（这一步的质量直接决定模型分析质量，值得花心思）
3. 分析时选中该模版

### 4.3 提示词层兜底统计（零代码获取粗略统计）

模版的 `extraRules` 里可以写：「本日志来自 XX 系统，失败特征是 XXException/关键词XXX，请统计各失败类型的次数并引用行号」。模型会按行号报告失败——精度低于轨道A，但不写一行代码。

## 5. 第二层：压缩去噪适配（compressor.py）

文件：[core/compressor.py](file:///c:/Users/11364/Desktop/log-analysis/core/compressor.py)

### 5.1 需要替换的内容（文件顶部三个常量）

```python
ROUTINE_PATTERNS = [("模型会话", ("豆包模型会话", "千问模型会话")),
                    ("路由选择", ("调用方显式指定模型",)),
                    ("阶段成功", ("阶段执行成功",))]   # ← 换成新项目的例行刷屏日志关键词
RE_TP_LINE = "线程池监控"                              # ← 换成新项目的监控类日志关键词（或 None）
FAILURE_KEYS = ("NonRetryableException", "阶段执行失败", ...)  # ← 换成新项目的失败关键词
```

### 5.2 判定规则

- **例行（routine）**：高频重复、看一条等于看一万条的日志 → 归类计数，原文不进模型（省 token 的大头）
- **失败（failure）**：匹配 FAILURE_KEYS 的记录 → 原文进模型提示词的「失败明细」（最多 50 条），帮助模型聚焦
- 其余：模板归并 + 数字脱敏 + 超 200 字符截断

### 5.3 怎么找新项目的关键词

拿到新日志后：

```powershell
# 看出现次数最多的前 20 种消息模式（找例行）
python -c "
from core.parser import parse_file
from collections import Counter
import re
c = Counter()
for r in parse_file('新日志.log'):
    head = r['msg'].split('\n')[0]
    c[re.sub(r'\d+', '#', head)[:60]] += 1
for k, v in c.most_common(20): print(v, k)"
```

出现几千上万次的模式 → ROUTINE_PATTERNS；含「失败/异常/超时/ERROR 语义」的 → FAILURE_KEYS。

### 5.4 不做的影响

压缩率下降（token 消耗变大），但功能完全正常——例行日志会被模板归并兜底，只是「例行日志计数」表数字无业务含义。

## 6. 第三层：统计口径适配（stats.py，核心工作）

文件：[core/stats.py](file:///c:/Users/11364/Desktop/log-analysis/core/stats.py)

这是业务耦合最深的一层。**如果新项目不需要精确统计，跳过本节**。

### 6.1 三个统计函数与替换点

| 函数 | 产出 | 要改什么 |
|---|---|---|
| `collect_failures` | 失败统计表 + 附录明细 | 顶部一组正则 + `collect_failures` 里的判定分支 |
| `collect_threadpool` | 线程池分时段负载 | `RE_TP` 正则（匹配新项目线程池监控的输出格式） |
| `collect_processed_users` | 分时段处理人数 | 触发关键词「批改流水线启动」（换成新项目「一个业务请求开始」的日志标识） |

### 6.2 通用业务量统计的抽象思路

处理人数统计的本质是：**找到「一个业务请求开始」的日志标识 + 唯一键（resultId）→ 按时间分桶去重**。换成新项目时：

```
新项目对应物：
  「批改流水线启动」 → 新项目的请求入口日志（如「订单创建 start」「收到请求 requestId=」）
  resultId           → 新项目的请求唯一键（orderId / requestId / traceId）
```

替换 `collect_processed_users` 里的 `if "批改流水线启动" not in head` 关键词即可，其余分桶去重逻辑完全通用。

### 6.3 失败统计的适配方法

`collect_failures` 目前识别 5 类事件。适配时：

1. 先用 §5.3 的方法摸清新日志里有哪些失败形态
2. 每类失败对应一个判定分支：**首行含某关键词 → 抽取 resultId（换成正则提取新项目的唯一键）→ 存入对应列表**
3. 三个通用原则（踩坑经验，务必保留）：
   - **事件判定只看 msg 首行**（`head = msg.split("\n", 1)[0]`），否则 Java 堆栈里的异常类名会被重复计数
   - **同一事件多行日志要去重**（参考 `seen_stage_fail` 的 `(stage, rid)` 键设计）
   - **ERROR 但内容是成功的日志**（疑似误用 ERROR 级别）要排除出失败统计

### 6.4 定位 SQL（web/index.html `genLocateSql`）

如果新项目也需要「从日志定位到数据库记录」：替换 `genLocateSql` 函数里的表名、库名、JOIN 链路。当前版本硬编码了 composition-ai 的 5 张表和测试/正式两套库名，纯前端字符串拼接，按新项目的表结构重写函数体即可（保留测试/正式环境切换与复制按钮的框架）。

## 9. 完整操作示例：从零接入一个新项目

假设要接入「order-service」的日志：

1. **解析验证**（先于一切）：`parse_file` 跑一遍，确认条数与字段 → 不过则改 parser.py（§3）
2. **建模版**：页面新建「日常巡检-order」：concern 写订单链路健康，focus 写 [支付超时, 库存锁定失败, 重试风暴]，extraRules 写「失败给出行号与 traceId」
3. **跑一次模型分析**：选「统计 + 模型分析」→ 看模型分析节的质量，迭代模版措辞（此时代码统计是空的，正常）
4. **（可选）压缩适配**：摸日志找例行/失败关键词 → 改 compressor.py 三常量
5. **（可选）精确统计**：
   - 入口日志关键词 + 唯一键（traceId）→ 改 `collect_processed_users`
   - 失败形态 → 改 `collect_failures` 分支与正则
   - 线程池/资源监控格式 → 改 `RE_TP`
   - （需要 DB 定位 → 重写 `genLocateSql`）
6. **补回归测试**（见 §10），新模版日志各留一份小样例在 tests/
7. 历史档案/台账自动兼容，无需迁移

## 10. 回归测试要求

每次适配后必须跑：

```powershell
python -m pytest -q
```

**必须新增的测试**（参考现有 tests/ 目录的写法）：

1. `test_parser.py`：新格式的样例行能解析出完整记录（时间戳含毫秒！）
2. `test_stats.py`：新口径的失败判定、去重、分桶
3. `test_report.py`：新统计结构能渲染进报告不抛 KeyError

**历史教训**（务必遵守）：

- 日志格式变更导致解析 0 条 → 压缩输出全空（已发生过一次）。**任何 parser 改动都要带新旧两种格式的回归样例**
- 新增统计字段时 report.py 若直接 `b['xxx']` 取值，旧测试数据没这个字段会 KeyError → 用 `.get()` 或同步更新测试数据
- 多行堆栈中的异常类名会被误计为独立事件 → 事件判定永远只看首行
