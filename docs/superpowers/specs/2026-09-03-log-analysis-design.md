# 日志智能分析工具 — 设计文档

日期：2026-09-03
状态：定稿待审
目标：本地个人使用的 Web 工具，每天晚上把当天项目日志（几百 KB ~ 几百 MB 的 Java logback 文本日志）上传，自动统计 + 模型分析，产出一份可回看的 Markdown 报告。

---

## 1. 背景与调研结论

### 1.1 模型能力事实（2026-09 调研）

| 模型 | 上下文窗口 | 最大输入 | 最大输出 | 输入价格 |
|---|---|---|---|---|
| GLM-4.6 | 200K | ~170K | 16K | ¥3-4/百万 tokens |
| DeepSeek / Kimi / 火山方舟 | 128K~256K 不等 | — | — | 同量级 |
| Claude Opus 5 | 1M (beta) | ~990K | 128K | $5/百万 |

- 存在 "Lost in the Middle"：塞满上下文时中间内容召回率明显下降。**单次可靠分析量取 10 万 tokens 以内**。
- 中大密度日志的换算：**1MB ≈ 60~80 万 tokens**（中文 1 token ≈ 1 字符，实测样例 8MB ≈ 500~650 万 tokens）。
- 结论：几百 MB 原始日志不可能直接喂模型，必须"代码压缩 + 分块"。

### 1.2 样例日志实测（composition-ai.log，8.03MB）

- 16,781 行 / 7,245 条完整记录（多行合并后），时间跨度 77 分钟。
- 级别分布：INFO 6,050 行、ERROR 1,190 行、WARN 5 行、多行续行 9,536 行（占 57%）。
- **ERROR 被当业务日志用**：成功消息（"批阅成功/SUCCESS/合规:true"）也打 ERROR，1,190 条 ERROR 里真正失败事件只有约 15 条。
- 压缩实测：8.03MB → **137,629 字符（1.6%）**，归并后 324 个模板组，估算 ~12.4 万 tokens，一次调用可容纳。
- 附带发现的真实信号：`作文批阅维度百分比转换数字异常: undefined%` ERROR × 288；`测试打分，这里已经引入了风控检测` INFO × 187。

## 2. 总体架构：双轨制

```
上传文件 → 解析(多行合并) ─┬→ 轨道A 结构化统计（纯代码，秒级，零成本）
                          └→ 轨道B 模型分析（压缩→切块→Map-Reduce，可选）
                                     ↓
                          报告合并 → reports/YYYY-MM-DD_HHMM_文件名.md
```

**轨道 A（确定性统计）**：失败事件统计、线程池分时段汇总。数字 100% 来自代码提取，模型不碰，绝对准确。
**轨道 B（语义分析）**：真假 ERROR 甄别、失败原因解读、按模版输出。用户可选择"仅统计"（免费）或"统计+模型分析"。

```

│   ├── compressor.py       # 模板归并 + JSON载荷截断 + 例行日志计数
│   ├── chunker.py          # 按记录切块（中文token估算）
│   └── analyzer.py         # 轨道B：Map-Reduce 调模型（httpx，并发3）
```

## 4. 解析层（parser.py）

- **流式逐行读取**：生成器产出，内存占用恒定在块级别，与文件总大小无关（支持几百 MB）。
- **编码容错**：UTF-8 `errors="replace"`，坏字节不中断。
- **多行合并**：`^\d{4}-\d{2}-\d{2} \d{2}:...` 开头视为新记录，其余续行（JSON 载荷、堆栈跟踪）归属上一条。解析结果为完整记录序列。
- **记录结构**：`{ts, thread, level, logger, msg}`，头部正则：
  `^(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{3}) \[([^\]]+)\] (TRACE|DEBUG|INFO|WARN|ERROR|FATAL)\s+(\S+) - (.*)$`
- 不匹配头部的行一律视为续行（与实测样例一致）。

## 5. 压缩策略（compressor.py）— 轨道B专用

按以下顺序处理，目标是把日志压到"模型值得看的部分"：

1. **例行流程日志计数化**（不进模型正文，只保留计数进报告头部）：
   - `豆包模型会话开始/结束（流式）`、`千问模型会话开始/结束` → "模型会话 ×N"
   - `调用方显式指定模型...命中厂商...` → "路由选择 ×N"
   - `阶段执行成功, ..., stage:XXX, costMs:N` → "阶段成功 ×N"（同时把 costMs 提取给轨道A做性能汇总）
2. **线程池监控行**：不进模型正文（322 条全给轨道A精确统计），模型只看到统计结果表。
3. **大载荷截断**：msg 长度 > 200 字符时保留前 200 字符 + `...[载荷截断]` 标记（保结构、去正文）。
4. **模板归并**：
   - 模板 key = `打码后的消息前 80 字符`；打码规则：≥4 位数字 → `#`、独立数字 → `#`、≥16 位 hex → `#`
   - 同 key 的记录归并为一组，保留**首条完整样例（含时间戳/线程/级别）+ 次数标记** `× N`
5. **产出**：`{压缩正文(带分组样例), 例行计数表, 模板组数, 压缩率}`。

**实测效果**：8.03MB → 137,629 字符（1.6%），324 个模板组。

## 6. 统计口径（stats.py）— 轨道A

### 6.1 失败事件统计（内置规则，全部要带 resultId 溯源）

| 统计项 | 匹配规则 | 输出 |
|---|---|---|
| 风控异常 | msg 含 `NonRetryableException`（含"风控异常"前缀行） | 次数 + 各条 resultId、时间 |
| 阶段失败（含流水线终止） | `阶段执行失败` / `阶段XX失败，流水线终止` | 按 stage 分组计数 + resultId 列表 |
| 批阅失败落库 | `作文批阅失败，已落库` | 次数 + resultId、失败阶段分布 |
| 并行网关成功分支数不足 | `并行网关成功分支数不足` | 次数 + resultId |

**不做**：JDBC 连接丢弃统计（用户明确不需要）。

**真假 ERROR 甄别**：ERROR 级别里 msg 含 `成功|SUCCESS|合规：true|完成` 的行标记为"疑似误用级别"，计数后不列为失败；剩余 ERROR 交模型解读。

### 6.2 线程池分时段汇总

- 匹配 `线程池监控[活跃线程数=X, 核心线程数=X, 最大线程数=X, 当前线程数=X, 历史最大线程数=X, 队列任务数=X, 队列剩余容量=X]`，提取 7 个指标。
- **时间桶粒度可配置**：默认 2 小时，页面可选 1/2/3 小时。
- 每桶输出：活跃线程数的**均值/峰值/谷值**、队列任务数的峰值、采样条数；另附**全天峰值**。
- 压力信号标记（代码判定，报告高亮）：`活跃线程数 ≥ 最大线程数×0.8` 或 `队列剩余容量 ≤ 总容量×0.2` 的时段。

## 7. 模型分析流程（analyzer.py）— 轨道B

### 7.1 切块（chunker.py）

- 对压缩后的正文按**记录边界**切块（绝不在记录中间切断）。
- 块大小默认 300KB，页面可调；token 估算 `tokens ≈ 字符数 × 0.9`（中文密度）。

### 7.2 Map-Reduce 管线

```
块1..块N + 模版提示词 ──并发3路──→ 各块中间摘要
（单块失败重试2次，仍失败标记"分析缺失"，不阻塞整体）
        ↓
若中间摘要总量 ≤ 单块上限 → 一次汇总
否则 → 每20份摘要二级归并 → 层级汇总 → 最终报告章节
```

- API 调用：OpenAI 兼容 `/chat/completions`（httpx），预置火山方舟 / Kimi / DeepSeek / 智谱 + 自定义 BaseURL/Key/模型名。
- 并发默认 3（尊重各家 RPM 限流量级），config.json 可调。
- 提示词组成：模版 JSON 渲染 + 压缩正文 + 轨道A统计结果（供模型做关联解读，如"失败集中时段 vs 线程池压力"）。

### 7.3 分析模式

- **仅统计**：只跑轨道A，秒级完成，零成本。
- **统计+模型分析**：轨道A + 轨道B。

## 8. 模版系统（templates/*.json）

```json
{
  "name": "日常巡检",
  "concern": "关注失败事件的原因分析和趋势",
  "focus": ["风控异常", "阶段失败", "线程池压力"],
  "outputFormat": "Markdown，含【结论】【异常明细】【建议】三节",
  "extraRules": "如发现失败集中在某时段，结合线程池负载给出关联判断"
}
```

页面可视化编辑（增删改、设默认），落盘为 JSON 文件。

## 9. 页面结构（web/index.html，单页三区块）

1. **上传+配置区**：文件上传（也支持填本地路径）、选模版、选分析模式、开关（时间桶粒度 1/2/3h、块大小 KB）。
2. **预估确认区**：上传后立即显示文件大小/行数/时间跨度/压缩后大小/块数/**预估成本（元）**/预估耗时。点"开始分析"才调模型。
3. **结果区**：报告渲染 + 导出按钮 + 历史报告列表（读 reports/ 目录按日期倒序）。

弹窗：**设置**（模型配置）与**模版编辑**。

## 10. 报告格式（reports/YYYY-MM-DD_HHMM_文件名.md）

```
# {日期} 日志分析报告
> 模式：统计+模型分析 | 模版：日常巡检 | 消耗：¥x.xx

## 一、核心指标（代码统计，精确）
   失败统计表（类型/次数/resultId 样例）
   线程池分时段负载表（均值/峰值/采样数）+ 全天峰值 + 压力信号高亮
   例行日志计数表（模型会话/阶段成功/路由选择次数）

## 二、模型分析（按模版）
   【结论】【异常明细】【建议】

## 三、附录：失败事件完整日志行（带原文件行号，便于溯源）
```

## 11. 错误处理与安全

- 单块失败重试 2 次后标记缺失，不阻塞整体。
- API Key 只存本地 config.json，任何报告/页面回显中脱敏。
- 后端仅监听 127.0.0.1，不对局域网暴露。

## 12. 测试验收（以样例日志为准）

- 轨道A核对：风控异常 3 次、EVIDENCE_EXTRACTION 失败 3 次、线程池监控 322 条正确分桶。
- 压缩核对：8.03MB → ~137K 字符、324 模板组。
- 端到端：仅统计模式（秒出）→ 完整模式（单块、成本 < ¥1）。
- 前端：上传→预估→确认→报告渲染→历史列表全流程。

## 13. 不做的事（明确排除）

- JDBC 丢弃统计；历史数据库（直接落文件）；压缩包/多文件上传；RAG/向量检索；用户权限体系。
- 二期候选（本期不实现）：完整 Drain 模板挖掘、定时任务自动拉取日志、多文件对比分析。
